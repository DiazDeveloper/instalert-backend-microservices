# ADR-001 — Extracción de Account y transición del monolito

Estado: implementado y verificado localmente; MySQL 9.7 local verificado posteriormente; contenedores y conciliación real pendientes. Fecha: 2026-10-09. Trazabilidad: HU1–HU3, AC-03, Sprint 1 del paquete de migración.

1. **Límite de servicio.** Account integra IAM y Profiles en una aplicación y una base exclusiva. Se reutilizan Spring Boot/Java 21, Spring Security, BCrypt, las autoridades `ROLE_USER`/`ROLE_ADMIN` y las necesidades de los modelos originales. El gateway MVC implementa rutas fijas de Strangler sin añadir un quinto servicio de negocio ni dependencias Spring Cloud. Los otros tres contextos permanecen en su código original con un adaptador de sesión HTTP y autorización mínima de referencias.
2. **Identidad explícita.** Un UUID identifica públicamente la asociación uno-a-uno entre identidad y perfil. El frontend envía UUID en operaciones de Account. El campo `id` del perfil es una referencia numérica de transición para los consumidores existentes; no es el ID IAM. La importación preserva el ID del perfil como `profile_id` y `legacy_profile_user_id`, y el ID IAM independiente como `identity_id`/`legacy_iam_user_id`. Reservar los IDs importados antes de habilitar registros nuevos evita colisiones. Los servicios siguientes migrarán esas referencias a UUID cuando se extraigan.
3. **SQL propuesto frente a comportamiento existente.** Se conservan las cinco tablas propuestas y sus FKs exclusivamente locales. Se agregan `avatar` y `current_location` porque existen consumidores reales; la ubicación es solo un dato de visualización de perfil. Nombre pasa a `display_name`; correo reside únicamente en identidad, autoridades en `identity_roles`, y `birth_date` es DATE. `token_version` posibilita revocar sesiones. Los timestamps UTC y bloqueo optimista existen en identidad/perfil; la tabla de roles se siembra con las dos autoridades del código original. No se usa la igualdad incidental de IDs como asociación.
4. **Contrato y seguridad.** Registro inserta identidad, perfil y asociación en una transacción; nunca admite autoridades desde el cliente. El rol de presentación se deriva de autoridades reales. Se protege perfil por propietario/admin; cambio de contraseña solo por propietario; listado completo/rol/desactivación por admin. El directorio autenticado no incluye correo/teléfono/fecha/ubicación/autoridades. DELETE desactiva identidad y revoca tokens para conservar referencias. Esto corrige el antiguo borrado exclusivo del perfil que dejaba credenciales activas.
5. **Sesiones.** Se conserva HS256 con clave externa Base64 exclusivamente en Account; UUID como `sub`, `iss=ms-account`, `aud=instalert-api`, `exp` de una hora por defecto, límite configurable 60–86400 segundos. El monolito valida cada Bearer en `GET account/session`, sin clave de firma ni consultas IAM locales. Una caída de esa validación cierra el acceso con 503, sin fallback a identidades antiguas. Cambiar contraseña, autoridades o desactivar invalida sesiones por versión/estado. Los JWT antiguos y cachés sin UUID se rechazan: el corte requiere iniciar sesión nuevamente. No hay convivencia silenciosa de emisores.
6. **Único escritor y reversión.** El escaneo del monolito excluye los beans, repositorios y entidades antiguos de Account; Hibernate solo valida los tres contextos restantes. El gateway envía todas las rutas Account al nuevo servicio y el monolito las deniega directamente. Las fuentes anteriores se conservan como referencia, no como componentes activos. Corte y reversión requieren respaldo, pausa de escrituras y conciliación; no se aplicó a datos reales.
7. **Infraestructura/evidencia.** Compose local usa dos instancias MySQL con usuarios separados; secretos externos y backend privado. La correlación se genera o valida en el gateway y se reenvía con las respuestas. Se evita crear una biblioteca transversal vacía: biblioteca distribuida/outbox y extracción de los siguientes servicios quedan para su sprint. Las pruebas usan H2 en modo MySQL y procesos Java 21; ese resultado no sustituye comprobar MySQL, contenedores o Azure.

Fuentes: paquete `InstAlert Contexto Migracion`, especialmente decisiones actuales, Sprint 1, SQL Account y revisión del backend/frontend originales. El plan antiguo de cinco iteraciones ADD y las tecnologías del PDF previo no sustituyen el alcance actual de dos iteraciones ADD y cuatro servicios.

Actualización de compatibilidad local: se conserva `account_status` y su CHECK del SQL original, UUID CHAR(36) y rol SMALLINT. Flyway V2 añade únicamente los campos ausentes y autoridades iniciales, con baseline V1 explícito para las tablas creadas manualmente. La validación del esquema detectó estas diferencias en MySQL 9.7; no se reemplazaron tablas.
